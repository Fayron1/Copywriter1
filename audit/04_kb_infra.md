## 1. 🔴 Находки

### 1.1. Telegram-бот не проверяет отправителя — любой чат может писать в базу и запускать генерацию

**Место:** `kb_update.py:432–441` (`handle_update`) + ветки команд/файлов (446–531).

```python
if not CHAT_ID:
    CHAT_ID = cid  # первый написавший становится владельцем
```

`CHAT_ID` из env **только устанавливается**, если пуст, но **никогда не проверяется** на соответствие входящему `cid`. Следствия:

- Если `TELEGRAM_CHAT_ID` в .env не задан: первый встречный, написавший боту, становится «владельцем», а любые последующие чаты **продолжают приниматься**: `/gen` запускает генерацию (расход DeepSeek/KIE-бюджета), присланный файл заливается в БЗ.
- Даже при заданном `TELEGRAM_CHAT_ID`: любой, кто найдёт бота по токену-логину, может (а) забить базу знаниям поддельным «законом» → **отравление RAG-фактов** → ложные цифры в будущих статьях (это прямой удар по продукту «экспертные статьи с паспортом фактов»), (б) гонять `/gen` за чужой счёт.
- Уведомления при этом уходят владельцу — проблема видна как «странная активность», не как запрет.

Это архитектурный допуск «бот приватный, токен никому не светится», но токен бота — не секрет в строгом смысле (логин бота публичен). **Фикс (направление):** в начале `handle_update` — `if CHAT_ID and cid != CHAT_ID: return` (+ лог); при пустом CHAT_ID — только /start с паролем-фразой.

### 1.2. Path traversal через имя файла из Telegram

**Место:** `kb_update.py:500–512`.

```python
filename = doc.get("file_name", "document")
...
dest = dest_dir / filename
dest.write_bytes(r.content)
```

`file_name` приходит из метаданных Telegram и не санитизируется. Имя вида `../../Copywriter1/.env` (с расширением .pdf в конце, чтобы пройти фильтр 502: `../../x.pdf`) записывает файл **вне** `KB_ROOT`. В связке с §1.1 это пишет произвольный контент в произвольный путь от имени процесса демона (на VPS — root).
**Фикс (направление):** `filename = Path(filename).name` + запрет `..`/слэшей.

## 2. 🟡 Средний приоритет

### 2.1. Устаревшие чанки остаются в Qdrant при обновлении существующего файла

**Места:** `loader.py:299–300` (uuid5 включает `content_hash`) + `loader.py:365–375` (prune).

Сценарий: файл `legislation/НК_РФ_2026.pdf` обновлён на диске (новая редакция под тем же именем). Новый текст → новые `content_hash` → **новые point_id** → upsert добавляет вторые версии чанков. `prune_folder` удаляет точки, чей `source_file` **не в списке живых файлов** — а у осиротевших старых чанков `source_file` тот же → они остаются. Итог: в коллекции лежат обе версии текста нормы; RAG может выдать устаревший чанк со скором не хуже нового. Заявленная идемпотентность («перезалив не создаёт дублей» — SYSTEM_OVERVIEW) верна **только для неизменённых файлов**.

Практический риск смягчается рабочим процессом (новые редакции часто приходят файлами с новым именем → старый файл удаляется → prune отрабатывает). Но путь «исправили опечатку в существующем файле» оставляет мусор молча.

**Фикс (направление):** перед заливкой папки удалять точки по фильтру `source_file == X` для каждого перезалитого файла (или полный delete-by-filter папки перед full-прогоном — заливка идемпотентна, страха нет).

### 2.2. Зависимость RAG от версии qdrant-client на VPS

**Место:** `rag.py:146–155`. Фильтр актуальности использует `models.IsNullCondition` (свежий API). Локально установлен qdrant-client **1.18.0** — все классы есть (проверено). Но loader/демон работают через `venv/bin/python` **на VPS** — версия там неизвестна. Если старее появления `IsNullCondition` → `AttributeError` → ловится общим except (rag.py:195–197) → **RAG молча возвращает пустой контекст для всех агентов** — деградация «статьи без фактов», видная только по логам. Важно, что это уже второй инцидент этого фильтра (комментарий 140–144 описывает случай, когда is_null выкинул 31k законодательных чанков — 2026-10-02).

**Фикс (направление):** зафиксировать версию в requirements + проверить `pip show qdrant-client` на VPS; в rag.py сделать try/except вокруг IsNullCondition (сейчас обёрнут только IsEmptyCondition).

### 2.3. Латентный переключатель провайдера эмбеддингов ломает совместимость молча

`copywriter_kb/config.py:25`: `EMBEDDING_PROVIDER` — `local` (e5, 768d) по умолчанию, `openai` (text-embedding-3-large, **3072d**) по env. Если где-то на VPS в .env останется/появится `EMBEDDING_PROVIDER=openai` (legacy-путь), `rag.py:89` получит 3072-мерный вектор запроса → `query_points` упадёт с dimension mismatch → общий except → **весь RAG молча отключён**. Векторы БЗ при этом 768d.
**Фикс (направление):** при старте pipeline сверять `len(query_vector)` с `get_dim()` (или info коллекции) и громко падать/логировать при расхождении; env-ветку openai пометить deprecated.
