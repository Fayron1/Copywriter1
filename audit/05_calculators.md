## 2. 🔴 Находки

### 2.1. «Всего нагрузка» не включает страховые взносы — систематическое занижение на 25–35%

**Место:** `tax_calculator.py:295` → `r.total_burden = r.vat_payable + usn_final + r.profit_or_ndfl_tax`.

**Живой прогон (демо пайплайна: 120 млн выручка, 78 млн закупок, ИП, ФОТ 12 млн):**

```
УСН + НДС 5%      итого = 9 600 000 ₽ (eff 8.0%)   ← взносы 4 854 390 ₽ В ИТОГЕ ОТСУТСТВУЮТ
ОСНО              итого = 13 922 000 ₽ (eff 11.6%)
```

Взносы (фикс 57 390 + 1% + 30% ФОТ = **4,85 млн**) реально платятся, но в `total_burden` не входят. При этом для УСН «доходы» налог уже *уменьшен* на них (механика зачёта), а для ОСНО они лишь снизили базу прибыли. Итог по деньгам: УСН5 = 6 + 3,6 + 4,85 = **14,45 млн** (таблица показывает 9,6), ОСНО = 13,92 + 3,6 = **17,52 млн** (показывает 13,92). Оба занижены, но **по-разному** → дельта сравнения смещена: реальный разрыв 3,05 млн, таблица показывает 4,32 млн (+42% к преимуществу УСН). В пограничных темах смещение способно развернуть вывод «что выгоднее».

Heart обязан вывести таблицу дословно, колонка называется «Всего нагрузка» — читатель прочтёт «все платежи государству». Это **самый значимый фактический дефект этапа**.
**Фикс (направление):** добавить в `total_burden` строку взносов (как минимум `r.insurance` для USN-«доходов» и `insurance_employer` для ОСНО), либо переименовать колонку и добавить явную строку «+ взносы» в таблицу/примечание. В обоих случаях — регресс-тест на «итого = сумма строк».

### 2.2. УСН «доходы минус расходы»: база без ФОТ/взносов и без минимального налога 1%

**Место:** `tax_calculator.py:216–227`.

```python
base = max(0, r.revenue_ex_vat - r.purchases_ex_vat)   # только закупки!
...
r.usn_after_reduction = r.usn_tax                      # минимальный налог не учтён
```

- База 15% считает только закупки: ФОТ, взносы работодателя и взносы ИП **не вычитаются** → систематическое завышение налога Д-Р (при том что ОСНО-ветка ФОТ вычитает — неравные условия сравнения).
- При базе ≤ 0 налог = 0, хотя по ст. 346.18 минималка — **1% от доходов**. Тема «что выбрать при высокой доле закупок» с кейсом в убыток получит «налог 0 ₽» — фактически неверное число.
- Сейчас из пайплайна ветка недостижима (pipeline жёстко передаёт `usn_object="income"` — находка этапа 2.6), но API модуля сломан для половины его декларированных сценариев. Аналогично в `marketplace_calculator:78` ветка `usn15` без минималки.

**Фикс (направление):** в base включить payroll + insurance_employer + взносы ИП; после `usn_tax = base × rate` — `r.usn_tax = max(usn_tax, revenue × 0.01)`.

## 3. 🟡 Средний приоритет

### 3.1. Marketplace-калькулятор: налог на прибыль ОСНО 20% вместо 25%

`marketplace_calculator.py:81` — жёсткий `0.20` и формула «× 20%». `tax_calculator.PARAMS_2026["profit_tax_rate"] = 0.25` (2026). Рассинхрон между двумя детерминированными модулями; забавная деталь — линтер norm_params умеет ловить «устаревшие 20%», а свой же модуль их выдаёт. Из пайплайна сейчас не стреляет (DEMO = usn6), но модуль экспортирует ветку `osno`.

### 3.2. math_validator: толерантность 2% бьёт легитимные округления

**Проверено кодом:** «выручка 120 млн × 6% = **7 млн**» → 🔴 МАТЕМАТИЧЕСКАЯ ОШИБКА (ожидание 7,2 млн; допуск 144 тыс. < разницы 200 тыс.). Округление до одной значащей цифры — нормальная практика в прозе статьи, а валидатор требует точность 2%. Эффект: ложные блокирующие 🔴 в publish-gate → churn переписываний Heart.

Дополнительно: `check_usn_reduction` (math_validator.py:140) жёстко считает `tax_before = revenue × 0.06` — для региональных ставок УСН 1–5% инвариант посчитается по 6% и даст ложный 🔴 УСН-ИНВАРИАНТ.

**Фикс (направление):** допуск по числу значащих цифр результата (округлено до 1 знака → допуск до ±5%), и игнор «круглых» результатов, делящихся без остатка; в check_usn_reduction читать ставку из текста/паспорта, а не константу.

### 3.3. Закупочный блок без модельной маркировки: конфликт с собственным линтером + DEMO-ставка

- `procurement_calculator.build_heart_block` (283–310) не содержит ни одного слова из `_MODEL_MARKER` norm_params («допущени», «условн», «модельн», «расчётн»...). При этом блок требует «использовать ЭТИ цифры дословно», а DEMO содержит **key_rate = 9,5%** — если фактическая ключевая на момент статьи другая, пени в статье считаются по чужой ставке, и маркировки «условный пример» нет. Когда Heart пишет «штраф составляет 475 000 ₽», `_UNVERIFIED_COST` даёт 🟡 ЦЕНА БЕЗ ИСТОЧНИКА (в ±1000 символах нет model-маркера) — шум гейта.
- Сравни: marketplace-блок содержит `assumptions_note` («допущения модели...» — маркер есть), но тоже без явной даты снимка тарифов.
- **Фикс (направление):** в build_heart_block/build_penalty_block добавить строку «Модельный сценарий с допущениями (ставка ЦБ 9,5% — проверь актуальную на дату)» — закрывает и линтер, и фактическую свежесть.

### 3.4. `draft_claim_extractor`: флагманские значения не извлекаются

**Проверено кодом** на контрольной строке «Порог... 20 млн. Ставка НДС 22%... Спецставка 5%... взносы — 57 390 рублей. Лимит 490,5 млн ₽. По ст. 346.13 НК РФ...»:

| Значение | Извлечено? |
|---|---|
| «22%», «57 390 рублей», «490,5 млн ₽» | ✅ |
| **«20 млн»** (без ₽) | ❌ — `_NUM_VALUE` требует ₽/руб/% после суммы |
| **«272,5 млн»** (без ₽) | ❌ — та же причина |
| **«5%», «7%»** (однозначные) | ❌ — шаблон требует ≥2 цифр или десятичную дробь |
| **«ст. 346.13 НК РФ»** | ❌ — сплиттер предложений режет фразу по периоду в «ст. » («По ст.» = 7 симв. → отброшен) |

Экстрактор — теперь **первая фаза** claim-check (незакоммиченная правка), т.е. покрытие утверждений молча сузилось ровно по флагманским паттернам системы (порог 20 млн, ставки 5/7%). Правовые ссылки фактически не извлекаются вовсе. Побочно: `match_to_sources` (60–74) — мёртвая функция (вызовов нет).
**Фикс (направление):** в `_NUM_VALUE` сделать валютный хвост опциональным при наличии единицы млн/млрд; разрешить `\d{1}\s*%`; в сплиттере не резать по «ст./п./ч./№» (негативный lookbehind) и добавить регресс на «ст. 346.13».

### 3.5. `check_value_conflicts`: контекст-окно мёртвое, исключение текстовое глобальное

`contradiction_checker.py:104–112`: `ctx = text[max(0, text.lower().find(pat.split("[")[0][:12])):][:2000]` вычисляется и **не используется** (к тому же `find` ищет регэксп-литерал «(?:порог|лим» — всегда −1). Реальная проверка `if not _COMPARE_MARKERS.search(text)` смотрит **весь** текст: одно «было»/«с 2026» где угодно глушит детектор конфликтов значений по всей статье. Правило почти не имеет силы на длинных текстах.

- **Уменьшение УСН на взносы** (п. 3.1 ст. 346.21): с работниками — за себя + 1% + за работников, cap 50%; без — до 100% — соответствует инварианту и кейсу статьи 25 (fix от 2026-10-02 действительно в коде).
- **Приведение к «без НДС»** (`_to_ex_vat`, деление на 1.22) и спецставки 5/7 без вычетов — методология согласована с НК-механикой УСН.

- **calc_security**: диапазоны ст. 44 (0,5–1% / 0,5–5%), ОИК ≥ аванса, антидемпинг 25%/1,5×/10% пол/15 млн — согласовано со снимком БЗ.

- **math_validator**: ловит кейс статьи 18 из докстринга; форматы чисел (пробелы, nbsp, запятая) парсятся корректно; NaN-гварды есть.
