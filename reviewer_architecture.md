# Ревизор (The External Reviewer) — архитектура и задачи

## Что это

Ревизор — независимый контролёр качества статьи, который запускается ПОСЛЕ того как Heart написал черновик и ДО того как Booster наводит SEO. Он не пишет текст — он находит причины, по которым статью нельзя безопасно публиковать.

## Позиция в конвейере

```
Brain (декомпозиция)
  → Fact-Finder (факты из RAG + карточки применимости)
    → Scout (тренды через интернет)
      → Engineer (структура статьи)
        → Heart (написание текста)
          → Claim Check (хеджирование неподтверждённых)
            → ★ РЕВИЗОР (адверсариальное ревью)
              → Booster (SEO/GEO)
                → Packager (контент-пакет)
```

## Модель

- **Текущая**: gpt-6-1-sol через KIE `codex/v1/responses` API
- **Предыдущая**: gemini-3.8-flash-openai — 5 статей подряд 0 правок при баллах 38-86, модель неспособна к адверсариальному ревью
- **Причина смены**: gpt-6-1-sol имеет reasoning effort (low→xhigh), поддерживает structured output и web search — это должно дать глубокий анализ вместо ленивого «approved: true»

## Провайдер и endpoint

```
POST https://api.kie.ai/codex/v1/responses
Authorization: Bearer KIE_API_KEY
Content-Type: application/json

{
  "model": "gpt-6-1-sol",
  "input": [
    {"role": "system", "content": [{"type": "input_text", "text": "..."}]},
    {"role": "user", "content": [{"type": "input_text", "text": "..."}]}
  ],
  "reasoning": {"effort": "high"},
  "stream": false
}
```

Ответ: `output[]` → искать элемент с `type: "message"` → `content[].text`.
Это НЕ chat/completions — другой endpoint, другой формат запроса и ответа.

Метод: `pipeline._call_codex_reviewer(system_prompt, user_msg)` (pipeline.py:2348).
Диспетчеризация в Surgical Edit Loop: если модель = gpt-6-1-sol → codex, иначе → стандартный _call_agent.

## Задача (системный промпт)

Ревизор получает:
1. Тему и ТЗ статьи
2. Persona block (кто читатель, какой масштаб бизнеса)
3. Каталог разделов с индексами
4. Claim-каталог: уже извлечённые утверждения с рисками и статусами верификатора
5. Полный текст статьи
6. Стилевые требования (если checklist — жёсткие правила структуры)

Его задача — найти основания, по которым статью НЕЛЬЗЯ безопасно публиковать:
- Рискованные утверждения без источника/условий/субъекта
- Нарушения юридической точности (смешение режимов, норм, субъектов)
- Шаблонность (одинаковые конструкции в каждом разделе)
- Категоричные выводы без оговорок
- Обещания, которые текст не доказывает
- Отсутствие сценариев, где совет НЕ подходит

## JSON-контракт ответа

```json
{
  "approved": false,
  "score": 75,
  "top_5_risky_claims": [
    {
      "claim_id": "L-001",
      "quote": "дословная цитата из статьи",
      "risk_reason": "почему рискованно",
      "required_proof": "что нужно для безопасной публикации",
      "publication_action": "ALLOW | REWRITE | REMOVE | BLOCK"
    }
  ],
  "claim_verdicts": [
    {
      "claim_id": "cl_000",
      "status": "VERIFIED | VERIFIED_WITH_LIMITS | UNSUPPORTED | CONTRADICTED | OUTDATED | NEEDS_HUMAN_REVIEW",
      "publication_action": "ALLOW | REWRITE | REMOVE | BLOCK"
    }
  ],
  "edits": [
    {"section_index": 0, "reason": "почему", "instruction": "что сделать"}
  ]
}
```

## Валидация (детерминированная, после ответа)

1. Пропущенные вердикты: каждый claim_id из каталога обязан иметь вердикт. Пропущенные → NEEDS_HUMAN_REVIEW + REWRITE автоматически
2. UNSUPPORTED/CONTRADICTED → approved принудительно false
3. REWRITE/REMOVE/BLOCK без записи в edits → конвертируются в правки (цитата мапится на раздел по подстроке)
4. approved=true + score<85 → approved отменён (фикс статьи 35)
5. approved=true при наличии UNSUPPORTED → противоречие, approved отменён

## Surgical Edit Loop

```
Итерация 1-3:
  1. Разбить черновик на H2-разделы
  2. Отправить Ревизору (каталог + текст + правила)
  3. Валидация ответа (пустые риски, противоречия)
  4. Если approved=true И score>=85 → break
  5. Если score>=90 → break
  6. Отфильтровать правки (пропустить уже одобренные разделы)
  7. Применить правки хирургически (только указанные разделы)
  8. Пересчитать score
Accept-Best: вернуть черновик с наивысшим баллом
```

## Что Ревизор НЕ делает

- Не переписывает текст сам — только выдаёт инструкции для правок
- Не проверяет стиль (это Mirror) — только смысл, точность и безопасность
- Не ищет ИИ-штампы (это Humanizer) — только риски содержания
- Не подсчитывает токены — это Budget Controller

## Известные проблемы

1. **Ленивость**: даже с claim-претекстом модель возвращала 0 рисков и 0 правок
   (5 статей подряд: баллы 38-86, edits: []). Claim-pretext (каталог утверждений
   в промпте + обязательные вердикты) должен это исправить, но ещё не проверен
   боем после смены на gpt-6-1-sol.

2. **Gemini-3.8-flash** — предыдущая модель — нестабильна (~50% запросов
   отдают internal error, pipeline ретраит). GPT-6.1 Sol может быть стабильнее.

3. **Баллы не коррелируют с качеством**: 38, 52, 72, 76, 78, 86 — диапазон
   слишком широкий при схожем качестве статей. Нужна калибровка.

4. **Не все типы рисков покрыты**: Ревизор фокусируется на юр. точности,
   но не проверяет математическую сходимость таблиц (это calc_gate),
   не проверяет свежесть законов (это amendment gateway).

## Идеи для оптимизации (для агента)

1. **Двухфазное ревью**: Phase 1 — Claim Auditor (вердикты по каждой карточке),
   Phase 2 — Reader-value Judge (стоит ли читать, уникальность, полезность).
   Разные промпты, возможно разные модели.

2. **Калибровка баллов**: собрать эталонные статьи с оценками от внешнего
   ревьюера (человека), обучить шкалу (few-shot примеры в промпт).

3. **Детерминированный претекст**: вместо надежды на модель — передавать
   конкретные вопросы для каждого типа риска: «Проверь: субъект нормы?,
   режим?, условия?, исключения?, дата актуальности?»

4. **Auto-escalation**: если Ревизор вернул 0 рисков, но lint_legal
   нашёл 🔴 — это противоречие → автоматическая вторая итерация с
   подсказкой «линтеры нашли следующие проблемы...»

5. **Кэширование вердиктов**: если раздел не менялся между итерациями,
   не пере-ревьюить его — экономия токенов.

6. **Structured output**: вместо свободного JSON — строгий JSON Schema
   через response_format (если gpt-6-1-sol поддерживает через codex API).
